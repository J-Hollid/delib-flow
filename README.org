#+title: delib-flow

`delib-flow` is an Emacs package for running guided AI-assisted workflows from
an Org heading at point.

This repository was built incrementally from a design-first process and is now
in a stabilization and hardening phase.

* User guide

`delib-flow` currently works as a guided control buffer around a deterministic
or adapter-backed workflow run started from an Org heading.

At a high level, the package does this:

- capture a frozen snapshot of the heading at point
- open a dedicated control buffer
- let you run one workflow stage at a time
- keep stage history, working context, and filing artifacts in one place
- require explicit review at key inspect and project-decision boundaries
- support deterministic local filing into your projects file and ZK

The control buffer is organized around these top-level sections:

- `Now`
- `Current result`
- `Filing preview`
- `Next actions`
- `Current context`
- `Details`

`Now` now starts with a compact decision strip plus a recommended-next-pass
block and quick actions, so the first screen answers the current stage,
blockage, recommendation, active selection, and filing-target questions more
directly. `Current result`,
`Filing preview`, `Next actions`, and `Current context` stay expanded after
refresh and action execution. `Details` stays folded by default and holds
verbose material such as the source snapshot, accepted working context, latest
prompt/input, latest raw output, grouped stage history, and audit status.

Internally, stage actions, cockpit rerendering, focused filing surfaces, and
shared filing-state mutation now run through common infrastructure rather than
stage-specific open-coded shells. The design and implementation documents now
describe those shared contracts as the current system, not as future roadmap
work.

Typical workflow:

1. Put point on an Org heading you want to process.
2. Run `M-x delib-flow-start`.
3. In the control buffer, run `Inspect Source`.
4. Review the inspect result and choose `Accept Inspect Result` or reject/retry.
5. Run `Match Project`.
6. Review the project decision:
   accept the match, reject it, or use `Choose Project Manually` when the
   candidate set is ambiguous or no-match.
7. Continue into retrieval, extraction, cloud-routing, reintegration, and
   filing stages as needed.
8. Review filing artifacts and use `File Approved Outputs` when ready.

Control-buffer usage:

- Use `n` and `p` to move between the main cockpit sections.
- Use `TAB` and `S-TAB` to move between rendered actions.
- Press `RET` or `a` to run the action at point.
- Work from the nearest action cluster:
  `Recommended next pass` or `Quick actions` in `Now`, `Filing actions` in
  `Filing preview`, or the
  broader `Next actions` list when you want the full downstream menu.
- Press `z` to toggle narrow-screen focus mode when you want the cockpit to
  keep only the current decision loop open.
- The next cockpit pass is planned to add:
  - local context menus for the current section
  - on-demand control hints you can request at any point
- Use the compact shortlist surfaces for selection-heavy steps:
  `Manual project selection` now shows a candidate table in `Now`, and
  `Artifact selection` now shows a filing shortlist in `Filing preview`.
- Treat the editable `Selection:` blocks in those areas as fallback entry
  paths when the chooser commands are not sufficient.
- In the filing workspace, `Staged content preview` now shows the exact text
  that will be inserted, and filed target buffers are opened as staged-unsaved
  previews rather than being written to disk automatically.
- The control buffer now behaves more like a special operational surface:
  it uses a tighter special-buffer key foundation, a persistent header line,
  and standard revert semantics wired to delib-flow refresh.
- Press `A` to approve the current pending inspect or project-match result.
- Press `r` to retry the current pending inspect or project-match stage.
- Press `g` to refresh the control buffer.
- Press `q` to abort the run.
- Press `?` to view the control-buffer key help.

Point behavior after rerender:

- If inspect or project match is pending review, point moves to
  `Current result`.
- Otherwise point moves to `Next actions`.
- A manual refresh preserves the current top-level cockpit section when no
  stronger workflow anchor applies.

Important current behavior:

- Only one active `delib-flow` run is supported at a time.
- The source snapshot is frozen when the run starts; later edits to the source
  heading do not change the active run automatically.
- `inspect-source` and `match-project` now have explicit review state:
  pending review, accepted, rejected, and superseded by retry.
- Retrying inspect or project match supersedes the prior reviewed result before
  the new candidate result lands.
- Old and superseded attempts appear only under `Details > Stage history`,
  grouped by stage with nested attempts.
- The control buffer is the primary UI. Some workflow branches rely on editing
  structured in-buffer blocks, but manual project choice and filing choice now
  foreground compact shortlist views and completion commands before the
  fallback block-edit path.

Current interactive entry points:

- `M-x delib-flow-start`
  Start a run from the Org heading at point.
- `M-x delib-flow-refresh`
  Public refresh command for the active control buffer.
- `M-x delib-flow-refresh-buffer`
  Rerender the active control buffer while preserving editable block state.
- `M-x delib-flow-dispatch-action`
  Execute the action at point in the control buffer.
- `M-x delib-flow-approve-current`
  Approve the current pending inspect or project-match result.
- `M-x delib-flow-retry-current`
  Retry the current pending inspect or project-match stage.
- `M-x delib-flow-abort-run`
  Abort the active run and finalize audit state.
- `M-x delib-flow-control-help`
  Show the control-buffer keybindings.

Most stage actions are intended to be triggered from the control buffer rather
than from standalone commands. The normal loop is to move to the relevant
section, step through its rendered actions, and execute the one that matches
the current decision point.

* Configuration

The package exposes these main `defcustom` variables:

- `delib-flow-my-projects-file`
  Path to the authoritative My Projects Org file used by project matching and
  deterministic project filing.
- `delib-flow-zk-root`
  Path to the searchable Zettelkasten root used for retrieval and note filing.
- `delib-flow-prompt-library-file`
  Path reserved for the prompt library file.
  The current deterministic workflow does not depend heavily on it yet, but the
  package exposes it as part of the intended contract.
- `delib-flow-example-structures-file`
  Path reserved for example structures used by later prompt-driven behavior.
- `delib-flow-audit-log-file`
  Path to the Org audit log file where run and stage records are appended.
- `delib-flow-general-note-template`
  Template used when deterministic filing creates a general PKM note.
  Supported placeholders: `${title}`, `${source-artifact}`, `${note-type}`.
- `delib-flow-project-support-note-template`
  Template used when deterministic filing creates a project-support note.
  Supported placeholders: `${title}`, `${source-artifact}`, `${note-type}`.
- `delib-flow-default-local-model`
  Default local model identifier recorded in run state and audit metadata.
- `delib-flow-default-cloud-model`
  Default cloud model identifier recorded in routing and audit metadata.
- `delib-flow-cloud-policy-profile`
  Default cloud sanitization policy profile. Supported values: `standard`,
  `strict`.
- `delib-flow-cloud-provider-policy-alist`
  Provider-specific cloud policy overrides. Entries can set `:enabled` and
  `:policy-profile`.
- `delib-flow-local-stage-adapter`
  Function used to execute local stages.
  By default this points at the built-in deterministic executor.
- `delib-flow-cloud-stage-adapter`
  Function used to execute cloud stages.

In practice, the minimum configuration for the current local deterministic
workflow is:

- `delib-flow-my-projects-file`
- `delib-flow-zk-root`

Useful optional configuration:

- `delib-flow-audit-log-file` if you want persistent run logs
- `delib-flow-next-action-capture-template`,
  `delib-flow-waiting-for-capture-template`,
  `delib-flow-project-capture-template`,
  `delib-flow-general-note-capture-template`, and
  `delib-flow-project-support-note-capture-template` if you want filed output
  to follow your own org-capture patterns
- `delib-flow-general-note-org-roam-capture-key` and
  `delib-flow-project-support-note-org-roam-capture-key` if you want
  reference-note filing to use entries from `org-roam-capture-templates`
- `delib-flow-default-local-model`, `delib-flow-default-cloud-model`, and
  adapter functions if you are wiring real model backends into the stage
  contract

* Setup

Minimal setup example:

#+begin_src emacs-lisp
(require 'delib-flow)

(setq delib-flow-my-projects-file "/absolute/path/to/my-projects.org")
(setq delib-flow-zk-root "/absolute/path/to/zk/")
(setq delib-flow-audit-log-file "/absolute/path/to/delib-flow-audit.org")
#+end_src

If you want deterministic filing to use your own org-capture patterns:

#+begin_src emacs-lisp
(setq delib-flow-next-action-capture-template
      "%(delib-flow-capture-project-child-heading)\n:PROPERTIES:\n:CREATED: %U\n:SOURCE_ARTIFACT: %(delib-flow-capture-source-artifact)\n:END:\n")

(setq delib-flow-waiting-for-capture-template
      "%(delib-flow-capture-project-child-heading)\n:PROPERTIES:\n:CREATED: %U\n:SOURCE_ARTIFACT: %(delib-flow-capture-source-artifact)\n:END:\n")

(setq delib-flow-project-capture-template
      "%(delib-flow-capture-project-heading)\n:PROPERTIES:\n:CREATED: %U\n:END:\n%(delib-flow-capture-project-first-item-heading)\n")

(setq delib-flow-general-note-capture-template
      "#+title: %(delib-flow-capture-note-title)\n#+filetags: :reference:\n\n- Filed from delib-flow\n- Source artifact: %(delib-flow-capture-source-artifact)\n")

(setq delib-flow-project-support-note-capture-template
      "#+title: %(delib-flow-capture-note-title)\n#+filetags: :project:support:\n\n- Filed from delib-flow\n- Project: %(delib-flow-capture-project-title)\n- Source artifact: %(delib-flow-capture-source-artifact)\n")
#+end_src

The capture templates above must be non-interactive. Avoid `%^...` prompts and
`%?`, because `File Approved Outputs` needs to complete in one operator action.

If you want reference-note filing to follow your existing org-roam note
destinations instead of delib-flow's fallback ZK path naming, set the
org-roam capture keys directly:

#+begin_src emacs-lisp
(setq delib-flow-general-note-org-roam-capture-key "w")
(setq delib-flow-project-support-note-org-roam-capture-key "w")
#+end_src

When either key is set, delib-flow resolves the note target path and staged
file content from the matching `org-roam-capture-templates` entry. This is
useful when org-roam already decides subdirectories, filetags, note headers,
and IDs.

The operator can choose the filing template from the control buffer with `T`
while a reference-note artifact is active. If the chosen org-roam template
needs extra target input, such as a zettel filename stem for a function-based
target, delib-flow requests that value at template-selection time and stores
it in the `Reference note capture` block.

For delib-flow filing, prefer string-based `file` or `file+head` targets when
possible. Function-based targets are supported only when the operator provides
the needed `Target path:` override ahead of filing.

Available helper functions for `%(...)` capture expansions:

- `delib-flow-capture-item-text`
- `delib-flow-capture-project-title`
- `delib-flow-capture-note-title`
- `delib-flow-capture-note-type`
- `delib-flow-capture-source-artifact`
- `delib-flow-capture-project-child-heading`
- `delib-flow-capture-project-heading`
- `delib-flow-capture-project-first-item-heading`

Legacy compatibility:

- `delib-flow-general-note-template`
- `delib-flow-project-support-note-template`

Those older `${title}`-style note templates still work. They are mainly useful
if you only want note-file customization and do not need full org-capture
expansion.

For slower local-model machines, the repo-local local-test helpers can now
start debug scenarios at later checkpoints instead of always replaying from
=source=. Use =M-x delib-flow-local-test-start-context-scenario= when you want
accepted inspect/project review plus filtered reference context already loaded,

so the local model is only spent on the stage you run after startup.

=context-ready= state for downstream stage testing: =action-rich-midpoint=,
=waiting-rich-midpoint=, and =reference-note-rich-midpoint=. Filing-focused
debug scenarios are also available: =filing-selection-mixed= for mixed
approval readiness and =filing-note-conflict= for deterministic reference-note
conflict review.

  source-type recovery, literal email enforcement, entity surfacing, and

  for ambiguity, no-match, unique contact disambiguation, and unique linked
  note disambiguation.
- =discover-reference-material= now uses a compact prompt and is currently
  behaving reliably in the built-in stress scenarios, with clean
  =candidate_titles= output instead of broad package echoing.
- =filter-reference-material= now produces retained working context rather than
  title-only retention, includes guards against no-candidate runs, and is in a
  usable state for downstream testing.
- =extract-actions=, =extract-waiting-for=, and =suggest-reference-notes= are
  now in a usable state for current field testing, with compact prompts and
  bounded parser recovery.
- Filing-focused debug scenarios are now available for downstream review and
  conflict handling: =filing-selection-mixed= and =filing-note-conflict=.
- Later debug checkpoints now replay deterministically even when the active
  local stage adapter is Ollama-backed, so scenario preload should not hang on
  background local-model calls.
- The next likely local-LLM hardening target is =integrate-into-source= or
  filing-stage output quality, depending on what field testing surfaces.

If you are resuming a local-LLM hardening session, the detailed stage-by-stage
test strategy and current progress snapshot are documented in

* Current capabilities

What you can use today:

- Source inspection with deterministic source typing for email, meeting-note,
  fleeting-note, reminder, or unknown.
- Project matching against your projects file, including ambiguity and no-match
  branches.
- Explicit project-decision review with accept, reject, retry, and manual
  override behavior.
- A control-buffer UI with public keybindings and point-based action dispatch.
- Reference-material discovery and filtering against your ZK.
- Draft artifact generation for actions, waiting-for items, and reference
  notes.
- Optional cloud-routing, sanitization, reviewed-package approval, cloud-stage
  execution, and reintegration flow.
- Deterministic filing into your projects file and note store.
- Audit logging of run state, stage inputs/outputs, and inspect/match review
  transitions.

Current limits to keep in mind:

- The control flow is implemented, but later-stage heuristics are still being
  refined.
- Retrieval and filtering are deterministic heuristics, not yet deeply
  explanation-rich.
- The prompt-library and example-structures settings are exposed, but the
  current package behavior is still more workflow-contract-focused than
  prompt-system-heavy.
- Adapter-backed model behavior depends entirely on the functions you assign to
  `delib-flow-local-stage-adapter` and `delib-flow-cloud-stage-adapter`.
- Later-stage ergonomics are improved, but retrieval/extraction heuristics are
  still where most refinement work remains.

* Upcoming Artifact Enrichment Redesign

The next workflow redesign direction is documented in:

- [[file:docs/design.org][docs/design.org]]
- [[file:docs/implementation-plan.org][docs/implementation-plan.org]]

The main shift is from a filing-centric batch model toward a shared artifact loop:

1. find candidates
2. select one candidate
3. enrich the selected candidate
4. regenerate only the selected candidate when needed
5. file or execute the selected enriched candidate

This direction will be piloted on reference notes first, then extended to actions, waiting-fors, and project proposals.
