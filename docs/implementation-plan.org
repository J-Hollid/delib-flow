#+title: delib-flow implementation plan

This document tracks the implementation plan for `delib-flow` separately from
the product and workflow design in [[file:design.org][design.org]].

It is intentionally execution-oriented. The design document defines what the
package should do. This plan defines the current understanding of the work,
open decisions that still require agreement, and the milestone sequence we
intend to implement.

* Milestone 1 outcome

Milestone 1 is complete enough to serve as the control-buffer foundation for
later stage execution work.

Delivered behavior:

- `delib-flow-start` opens a dedicated Org-mode control buffer from the heading
  at point.
- The run captures and preserves a frozen source snapshot.
- The control buffer renders the planned top-level workflow sections.
- The buffer supports one active run at a time.
- Structured valid-next-action objects are present and rendered from state.
- Direct editable regions exist for the working-context slice and operator
  notes.
- Editable block contents sync back into run state and survive refresh.
- Managed regions are protected from casual editing.
- Managed-region damage is detected and reflected in action state.
- Refresh now rerenders section-by-section instead of rebuilding blindly.
- Validation gates are implemented and passing.

Known Milestone 1 limits:

- No prompt resolution yet.
- No adapter-backed model execution yet.
- No audit-log append yet.
- No deterministic filing yet.
- No rich editable-artifact validation beyond the current block lifecycle and
  conflict checks.

* Milestone 1 learnings

These are the main implementation learnings that should shape Milestone 2 and
later work.

- The complexity gate materially affected architecture in a good way.
  Large renderer and dispatcher functions had to be split into small helpers,
  which made the control-buffer code easier to test and reason about.
- Direct in-buffer editing is viable, but only with explicit ownership rules.
  The buffer became much more stable once editable block bodies and
  package-managed regions were treated as separate classes of content.
- Refresh preservation must be treated as a state-sync problem first and a UI
  redraw problem second.
  Editable text only became reliable once it was synced into run state before
  rerender.
- Text-property protection is workable, but boundary behavior matters.
  Empty editable blocks exposed read-only edge cases, which means future
  editable surfaces should be added with explicit insertion-boundary tests.
- Section-by-section rerender is a better default than whole-buffer redraw for
  this package.
  Even before anchors are used more aggressively, partial section refresh keeps
  the buffer model aligned with the design intent.
- Coverage gating was easiest to sustain once helper functions stayed small and
  single-purpose.
  This reinforces the current implementation style for future slices.
- The action layer benefited from being introduced before real stage execution.
  It now provides a stable place to attach legality, conflict handling, and
  later dispatch semantics.

Implications for Milestone 2:

- Define the generic stage execution contract in the same small-helper style.
- Keep stage input assembly separate from rendering and dispatch.
- Treat prompt packages and normalized stage results as state objects first,
  rendered views second.
- Preserve the current gate discipline: no new stage machinery should land
  without passing coverage and complexity validation.

* Milestone 2 learnings

- Introducing the stage contract before richer domain stages was the right
  order; it gave `Inspect Source` a place to land without hard-coding stage
  behavior directly into actions or rendering.
- Stage-history rendering and working-context updates should be kept separate.
  A stage can affect both, but the update paths should remain independent so
  future stages do not entangle history persistence with context presentation.
- Descriptor-backed stage execution keeps prompt IDs, labels, executors, and
  normalizers in one place, which should scale better than per-action bespoke
  logic.
- Failure entries are worth recording even in the minimal contract; they make
  retry and diagnostics semantics easier to extend later.
- Deterministic local heuristics are a good fit for early project matching.
  They let the workflow unlock the next branch without depending on model
  access for a decision that should remain inspectable and cheap.
- Reusing the filing surface for no-match project creation kept the branch
  smaller and more coherent.
  The project-proposal stage could land without inventing a separate review UI
  because the project artifact already fit the same integrate/file path.
- Reusing the existing project-match state shape for manual selection was also
  the right move.
  Downstream stages did not need to distinguish ordinary matched state from a
  manual override except where retry visibility mattered.
- Stage-dependent next actions should be derived from accepted workflow state
  rather than from stage order alone.
  `Match Project` changed the legal next-step set in a way that the action
  layer could represent cleanly once the stage result lived in run state.
- Retrieval behaves better as a separate candidate-collection stage than as
  immediate retained-context mutation.
  Keeping retrieved candidates distinct from filtered or accepted context
  preserves the intended later review step.
- Treating retained context as the output of filtering instead of discovery
  simplified the workflow model.
  It keeps the meaning of `:retained-context` stable for later artifact stages.
- The filing-preview section became useful as soon as one stage wrote draft
  artifacts into filing state.
- Keeping cloud execution separate from reintegration was the right boundary.
  It makes the cloud adapter easier to test and keeps local acceptance logic
  out of the provider handoff path.
- Editable cloud review needed a dedicated post-stage rerender path.
  Reusing the interactive refresh logic after stage execution clobbered freshly
  produced review text, so stage commands now rerender without first resyncing
  stale buffer state.
- Approved artifacts need an explicit state transition rather than being
  inferred from draft existence alone.
  Making filing selection its own stage produced a cleaner review loop than
  promoting approvals inside `Integrate into Source`.
  That keeps reintegration focused on context state and lets filing review
  operate one item at a time.
- Deterministic filing works best when artifact kinds own their own target
  resolver.
  Project-child insertion and reference-note creation were simple to add once
  the approved-item kind already carried enough information to choose a target.
- Audit logging is easiest to keep correct when it is attached to the single
  stage-finalization boundary.
  Updating audit state anywhere else would have duplicated failure and cloud
  path logic unnecessarily.
- Routing state became easier to reason about once it lived in the same stage
  contract and history machinery as artifact-producing stages.
  That suggests sanitization should be added as the next explicit stage rather
  than as implicit side effects on actions.
- Treating sanitization as its own stage produced a cleaner boundary than
  folding redaction into the cloud-routing decision.
  It keeps the run state honest about what is merely requested versus what is
  actually prepared for review.

* Project constraints

These constraints should be treated as enforcement gates for implementation
work, not as optional quality goals.

- Test coverage must remain at or above 90 percent, and this must be validated
  as part of implementation work.
- Cyclomatic complexity must remain at or below 5 per function or equivalent
  unit under the chosen validator, and this must also be validated.
- If a proposed implementation slice cannot meet these constraints cleanly, the
  slice should be decomposed further before code is merged.

Validation design:

- `ERT` in batch mode should be the authoritative test runner.
- Coverage validation should be implemented as a project-local command that
  instruments Emacs Lisp test execution, computes repository coverage, and
  fails when coverage is below 90 percent.
- Cyclomatic complexity validation should be implemented as a project-local
  Emacs batch command that analyzes Emacs Lisp function forms and fails when
  any function exceeds complexity 5.
- These validators should be runnable both locally and in CI with the same
  command surface.

Recommended command contract:

- `make test`
  Runs the authoritative batch `ERT` test suite.
- `make coverage`
  Runs coverage instrumentation and fails if total validated coverage is below
  90 percent.
- `make complexity`
  Runs the Emacs Lisp cyclomatic complexity validator and fails if any function
  exceeds 5.
- `make validate`
  Runs `test`, `coverage`, and `complexity` as the full project gate.

Recommended repository layout for validators:

- `Makefile`
  Public command surface for local and CI validation.
- `scripts/`
  Small validation entry points or wrappers if the commands become too large
  for inline Make recipes.
- `test/`
  Test definitions and any shared test helpers.

Complexity policy:

- Complexity should be measured per `defun` and other equivalent top-level
  executable units we intentionally decide to validate.
- The validator should count standard branch and path-increasing constructs in
  Emacs Lisp, such as `if`, `cond`, `when`, `unless`, boolean branching forms,
  `pcase` branch paths, and loop-like control structures.
- The validator should ignore comments, docstrings, and data-only forms.
- Generated code, if any appears later, should be excluded explicitly rather
  than implicitly ignored.
- If a helper is hard to understand but technically below complexity 5, we
  should still refactor when appropriate; the validator is a floor, not a full
  readability guarantee.

Coverage policy:

- Coverage should be evaluated for repository Emacs Lisp source under the main
  package, not for external dependencies.
- Test helper code may be excluded if needed, but exclusions should be explicit
  and kept minimal.
- New package logic should not be merged with untested branches on the theory
  that aggregate coverage remains above the threshold.
- If aggregate coverage remains above 90 percent but a new slice adds obvious
  untested paths, the slice should still be extended with tests before merge.

* Current understanding

- `delib-flow` starts from the Org heading at point and captures a frozen source
  snapshot for the duration of the run.
- The package presents workflow state in a dedicated Org-mode control buffer.
- The workflow is human-guided rather than autonomous.
- Version 1 inputs are limited to imported email Org items and meeting notes in
  daily notes.
- Version 1 is local-first. Cloud use is optional, stage-specific, and only
  allowed through a sanitization and explicit approval path.
- Stage outputs are reviewable artifacts, not direct source mutations.
- Filing must be deterministic and scoped to explicit approved actions.
- The system must preserve an audit trail sufficient for trust, review, and
  diagnostics.

* Requirements summary

** Core workflow requirements

- Preserve the source item unchanged while deriving working context and filing
  candidates from it.
- Represent workflow progress as stage history plus a current decision and valid
  next actions.
- Allow the human to inspect, retry, edit, approve, skip, or abort at
  stage-appropriate points.
- Keep the control interface constrained to currently legal actions rather than
  open-ended command entry.

** Data and state requirements

- Maintain a structured run state containing source snapshot, working context,
  stage results, approvals, filing candidates, routing metadata, and audit
  metadata.
- Record enough per-stage input and output data to support regeneration,
  diagnostics, and later audit-log append.
- Keep sanitized cloud packages separate from local non-sanitized working
  context.

** Integration requirements

- Match against the authoritative My Projects file.
- Retrieve candidate context from Org-roam and or `rg`-based PKM search when
  relevant.
- Support one configurable local model adapter and one configurable cloud model
  adapter shape.
- File approved artifacts through deterministic Emacs and Org operations,
  preferring capture templates where appropriate.

** Reliability requirements

- Keep runs alive across stage failures when possible.
- Surface malformed output, timeout, dependency, and partial filing failures
  clearly in workflow state.
- Avoid silent fallback across local and cloud execution paths.

* Open design decisions

These are the main decisions that still look implementation-shaping rather than
purely cosmetic.

1. Prompt storage and versioning
   The design depends on stable prompt IDs and prompt versions. We need to
   decide how prompts are resolved from Org, how versions are encoded, and what
   exact snapshot is persisted into audit state.
2. Stage result normalization format
   The design requires Org-native normalized outputs, but not the exact schema
   for each stage result. We need a concrete internal format that is stable
   enough for rendering, approval, filing, and audit.
3. Project matching strategy
   The matching criteria are described, but we still need to decide whether
   version 1 uses simple heuristics first, model-assisted ranking, or a hybrid
   pipeline.
4. Reference retrieval pipeline
   Weighted retrieval and filtering are specified conceptually. We need to fix
   the concrete retrieval inputs, scoring scheme, and whether filtering is
   heuristic, model-assisted, or both.
5. Filing target abstraction
   The filing contract is clear about deterministic actions, but not the
   internal abstraction for addressing a project item, metadata drawer, support
   note, or capture target.
6. Audit-log write timing details
   Audit logging should arrive before deterministic filing, and stage data
   should be appended incrementally for diagnostics. We still need to decide
   the exact append checkpoints and what minimum data should be written before
   a stage is fully approved.

* Agreed planning decisions

These decisions are settled unless we explicitly revise them later.

1. Adapter boundary
   Recommendation: define one stage-execution adapter contract shared by local
   and cloud paths, with provider-specific configuration behind it.
   The adapter should accept a stage descriptor plus a prepared input package
   and return a structured result object with provider metadata, raw output,
   normalized output or normalization failure, and execution status.
   Rationale: this keeps stage orchestration uniform and makes cloud routing a
   policy decision rather than a separate execution architecture.
2. Human editing model
   Editable artifacts should be edited directly inside the control buffer
   before selecting the next action.
   Rationale: that matches the guided-workflow model and keeps operator context
   visible while reducing buffer-hopping during review and retry flows.
   Representation: use package-managed headings and section structure with
   explicit editable blocks for artifact text, prompt text, and context slices.
   This should give rerendering stable anchors while preserving direct editing.
3. Audit-first sequencing
   Audit logging should be implemented before deterministic filing.
   Rationale: audit data is part of the trust model and provides diagnostics
   while the more mutation-heavy filing work is being built.
4. Control-buffer contract defaults
   Use explicit `#+begin_delib-edit` blocks for editable content, stable
   in-buffer structural anchors for managed-region lookup, read-only managed
   regions plus conflict detection, section-by-section rerendering, snapshot
   comparison for edit tracking, button-like valid actions in the action
   section, and an edit lifecycle that starts with `clean` and `edited`.
5. Internal contract defaults
   Use a fixed-domain top-level run-state plist with separate business and UI
   concerns, plist-backed editable-block objects keyed by stable IDs,
   structured valid-action objects rather than plain strings, and persistent
   in-buffer anchor IDs as the source of truth for section lookup.

* Recommended working assumptions

These are the assumptions I recommend unless you want to decide otherwise before
implementation:

- Use a structured plist-based run state first, since the scaffold already uses
  that representation.
- Treat the control buffer as a guided mixed-mode surface: stable workflow
  structure remains controlled by the package, while editable stage artifacts,
  prompts, and context slices are intentionally writable in their designated
  regions before action selection.
- Use a mixed representation for that surface: package-managed headings and
  explicit editable blocks rather than making whole sections free-form.
- Define the full top-level section and subsection contract now rather than
  allowing section structure to emerge ad hoc during implementation.
- Implement project matching and retrieval with deterministic heuristics before
  introducing model-assisted ranking in those stages.
- Treat audit logging as incremental and diagnostics-oriented, with append
  points occurring no later than stage completion and preferably also at key
  review checkpoints when useful.
- Keep version 1 focused on the local-only path first, while designing the data
  model so the cloud sanitization path can be added without restructuring run

2. Control-buffer document contract
- Lock down the top-level section order already present in the scaffold.
- Define the required subsection layout for each top-level section in Milestone
  1, even when the content is still placeholder or empty.
- Decide which parts of each section are package-managed, which are
  intentionally editable, and which are purely informational.
- Introduce stable markers or text properties so the package can find and
  re-render managed regions without treating the whole buffer as free text.
- Ensure re-rendering can preserve user edits in designated editable regions.

Deliverables:

  `Stage history`, `Current decision`, `Valid next actions`, `Filing preview`,
  and `Audit status`.
- A first pass at region ownership rules for the control buffer.

Proposed section schema:

`Source`
- Managed heading and managed subsections only.
- Required managed subsections:
  - `Title`
  - `Source metadata`
  - `Snapshot`
- `Source metadata` should include file, ID, outline path, source type, and
  run start metadata as available.
- `Snapshot` should render the frozen source text in a non-editable example or
  equivalent managed block.
- No editable blocks in this section during Milestone 1.

`Working context`
- Managed heading with both managed and editable subsections.
- Required managed subsections:
  - `Context status`
  - `Retained context`
  - `Editable working slice`
- `Context status` is managed and summarizes whether inspect output, retrieved
  context, filtered context, and cloud-sanitized context exist yet.
- `Retained context` is managed display content reflecting the current accepted
  context state.
- `Editable working slice` contains one or more `#+begin_delib-edit` blocks for
  operator-adjustable context text.
- Editable blocks here are the primary Milestone 1 proof of the direct
  in-buffer editing model.

`Stage history`
- Managed heading with managed per-stage subtrees.
- Required managed subsections:
  - `History status`
  - stage entries, when present
- Before stage execution exists, `History status` should state that no stages
  have been run.
- Later stage entries should use stable managed subheadings and may contain
  editable blocks only where the workflow explicitly allows retry editing.
- Milestone 1 does not need editable blocks in this section yet.

`Current decision`
- Managed heading with mixed managed and editable content.
- Required managed subsections:
  - `Decision status`
  - `Operator notes`
- `Decision status` is managed and states the current unresolved choice,
  blockers, and expected next step.
- `Operator notes` contains a `#+begin_delib-edit` block for human notes that
  may influence the next action choice.

`Valid next actions`
- Managed heading with managed action entries only.
- Actions should render as button-like entries with machine-readable identity,
  label, status, and optional reason text.
- Supported statuses should include at least `available`, `blocked`, and
  `placeholder`.
- Blocked actions must show why they are unavailable.
- This section should not contain editable blocks.

`Filing preview`
- Managed heading with managed subsections only in Milestone 1.
- Required managed subsections:
  - `Preview status`
  - `Approved artifacts`
- Until filing exists, this section should explicitly state that no filing
  preview is available.
- Editable blocks are deferred here until filing workflow demands them.

`Audit status`
- Managed heading with managed subsections only in Milestone 1.
- Required managed subsections:
  - `Run audit state`
  - `Stage audit readiness`
- This section should report whether audit logging is unimplemented, pending,
  or ready in later milestones.
- No editable blocks in this section during Milestone 1.

Region ownership rules:
- Managed headings, managed subsection titles, action entries, and frozen source
  snapshot content are package-owned and should be read-only.
- `#+begin_delib-edit` blocks are user-editable and tracked against the latest
  rendered snapshot.
- If package-owned text is modified, the workflow should detect the conflict and
  block the next action until the region is restored or rerendered.
- Section rerendering should replace only managed regions for that section and
  preserve editable block contents whenever anchors still match.

3. In-buffer editing model

Deliverables:

Editable block contract:
- Syntax should use `#+begin_delib-edit <kind>` and `#+end_delib-edit`.
- `<kind>` should initially support at least `context` and `notes`, with room
  to add `prompt`, `artifact`, and `sanitized-context` later.
- Each editable block should map to a stable internal identifier in run state.
- Edit lifecycle should start with `clean` and `edited`.
- Edit state should be computed by comparing block contents against the last
  rendered or last accepted snapshot for that block.
- Selecting an action should validate editable blocks first and block progress
  if managed-region conflicts exist.

Proposed editable-block object schema:

`(:id context-main
  :kind context
  :section "Working context"
  :heading-path ("Working context" "Editable working slice")

  :current-text ""
  :accepted-text ""

  :validation-message nil)`

Field notes:

- `:current-text` is the last known buffer content snapshot.
- `:accepted-text` is reserved for later use when edit acceptance becomes more

current scaffold state model with the agreed run-state contract and lock that
contract down with tests before UI behavior becomes more complex.

- No action buttons yet.
- No editable block rendering yet.
- No section-by-section rerender yet.
- No explicit lifecycle commands beyond what is necessary to keep
  `delib-flow-start` coherent under the new state shape.

** Known implementation risks

- Removing `view-mode` too late will complicate every later step; it should be
  treated as an early change.
- If anchor IDs are not introduced before rerender work, later buffer-preserve
  logic will be brittle.
- If action computation stays string-based too long, the control buffer will
  need to be rewritten again before stage execution.
- Tests that only assert visible text will be too weak; Milestone 1 also needs
  state-shape and lifecycle assertions.
- Coverage and complexity validation may force smaller implementation slices
  than the architectural sequence alone would suggest.
- If validation commands are not introduced early, later work may accumulate in
  ways that are expensive to split back down under the complexity ceiling.
