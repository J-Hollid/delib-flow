* Design learnings from Milestone 1

- The control buffer works better as a mixed managed/editable document than as a
  globally read-only view.
- Editable workflow surfaces need explicit ownership boundaries and refresh
  rules to remain reliable.
- Section-by-section refresh is a better fit for this design than whole-buffer
  redraw once user-editable content exists.
- A structured action layer is useful even before real stage execution exists,
  because it provides a stable place for legality, conflict, and review-state
  behavior.

* Control-buffer redesign direction

The current control buffer is functionally rich, but it still asks the operator
to parse too many equally weighted surfaces before taking the next step. The
next UI pass should optimize for decision-making speed, readability, and low
friction instead of adding more information to the same viewport.

** Primary operator goals

- See the current workflow state in one screen without scanning the whole
  buffer.
- Understand the one recommended next step quickly.
- See the exact consequence of filing before committing to it.
- Move through stage review and filing loops without repeated long scrolls.
- Distinguish clearly between current decision context, supporting detail, and
  historical/debug material.

** Emacs UI model

- The control surface should move toward a =special-mode=-style operational
  cockpit rather than a general-purpose document buffer.
- The main interaction loop should favor buttons, section navigation, minibuffer
  completion, and focused review commands over broad free-form editing.
- The control surface should optimize explicitly for terminal Emacs on a narrow
  viewport, including phone-sized SSH sessions where only one small work area
  can remain visible at a time.
- Editable in-buffer regions should remain available only where operator-authored
  free text is genuinely valuable, such as notes or conflict rewrite text.
- Selection-heavy states should prefer tabular presentation over prose lists.
- Consequence-heavy actions such as filing should present a stable side or
  sibling preview window instead of burying the result in lower sections.

** Target information hierarchy

The top screen of the control buffer should answer these questions in order:

1. What stage am I at?
2. What is blocked, if anything?
3. What is the recommended next action?
4. What item or project is currently selected?
5. If I file now, where will it go?

Everything else is secondary and should be visually lower-priority or collapsed
by default.

** Target control-buffer layout

The redesign target is a cockpit with these priorities:

- Top strip
  - run status
  - current stage
  - recommendation
  - active selection
  - immediate filing target preview when relevant
- Primary work area
  - actions available at point
  - current result
  - action-relevant context
  - staged output preview
- Secondary detail area
  - alternative actions
  - draft backlog
  - conflicts
  - stage history
  - audit and debug detail

This is intentionally different from a chronological report. The operator
should not have to read the workflow in historical order to decide what to do
next.

** Mobile-terminal target

The cockpit should also work well through terminal Emacs over SSH on a narrow
screen. That changes the design bar:

- one viewport should foreground the current decision loop rather than multiple
  equal-priority sections
- dense explanatory prose should be replaced by short state, why, and next
  lines
- long sections should collapse by default and reopen only when explicitly
  requested
- sibling previews should be preferred over forcing large scroll jumps
- action discovery should not depend on remembering many global keys

The operator should be able to make steady progress with one hand on a phone
keyboard and minimal scrolling.

** Recommendation and action model

The cockpit should foreground three distinct action layers:

- `Recommended next pass`
  - exactly one best next workflow pass when the system has a strong default
  - why that pass is recommended right now
  - one or two nearby alternatives when the recommendation is optional
- `Quick actions`
  - the small context-valid subset that should be reachable without scanning
    the whole buffer
  - each action should surface its outcome in one short line
- `More actions`
  - the broader legal action list for operators who want the full downstream
    menu

This makes the dominant path visible without hiding expert control.

** Context menus and help

Action discovery should not rely on the operator scanning the whole cockpit or
memorizing all bindings.

- Every major work area should support a local context menu.
  - `Now`: run-stage and recommendation actions
  - `Current result`: accept, reject, retry, compare, explain blocked state
  - `Filing preview`: choose artifact, choose template, preview target, file,
    open staged buffers
  - `Current context`: inspect retained evidence, prune, reopen excerpts
- A control-hints surface should be available at any time.
  - global keys
  - keys valid in the current section
  - current recommended next pass
  - current blocked reasons
  - current preview or filing consequence explanation

The control-hints surface should be lightweight enough to open and close
frequently during terminal use.

** Focus-mode target

The cockpit should support an explicit focus mode for narrow screens.

- Focus mode hides lower-priority sections and keeps only:
  - decision strip
  - recommended next pass
  - quick actions
  - one active work area such as current result or filing workspace
- Historical, debug, and backlog-heavy surfaces should be easy to restore but
  should not compete with the active decision loop while focus mode is on

This is intended as a first-class operating mode rather than a cosmetic toggle.

** Filing-workspace target

The filing workspace should remain the most consequence-heavy area in the
cockpit, especially on small screens. Its active loop should fit into one
viewport with these priorities:

- currently selected artifact
- recommended filing action
- exact file target
- selected capture template
- staged content preview
- explicit saved versus unsaved state

The operator should not need to scroll to another section to understand what a
filing action will do.

** Filing-loop target

The filing loop should be redesigned around one viewport containing:

- the currently selected artifact
- the actions available for that artifact
- the exact planned target location
- the staged content preview that would be inserted

Backlog artifacts, rejected items, older conflicts, and filed-location history
should remain available, but they should not compete with the active filing
decision by default.

** Selection model

- Manual project selection and filing-artifact selection should use completion
  commands and tabular views as the primary interaction model.
- Free-text =Selection:= editing should become a fallback path rather than the
  normal path.
- Candidate comparison views should show compact, decision-relevant columns such
  as title, status, kind, warning count, and target summary.

** Navigation model

- Global keys should stay minimal and memorable: refresh, quit, next/previous
  section, next/previous button, activate, help.
- Section-local actions should be discoverable at point and invokable without
  searching other parts of the buffer.
- The operator should be able to stay within the currently relevant section for
  most loops instead of jumping between far-apart parts of the cockpit.

** Visibility and disclosure model

- The current decision strip and current action area should always be expanded.
- Action-relevant previews should be auto-expanded.
- Historical, audit, and debug sections should be available but collapsed by
  default unless the current state specifically depends on them.
- Buffer motion after rerender should preserve local context when possible
  instead of aggressively pulling point back to a broad top-level anchor.

** Best-practice alignment

This redesign intentionally follows established Emacs patterns:

- =special-mode= conventions for generated operational buffers
- Help-style button navigation with =TAB=, =S-TAB=, and =RET=
- Magit-style section navigation and section-local behavior
- tabulated list presentation for row-oriented comparisons
- predictable temporary-window previews for supporting displays

The goal is not to imitate these packages visually, but to adopt their stronger
interaction model for a high-frequency operator workflow.

* Reference material discovery
- Inspect source should identify search terms to search the PKM.
- Discovery should include directly attached project reference material when a project is known.
- Directly linked project material is the highest-priority retrieval source.
- The broader PKM scan should use notes under `/zk` as the searchable zettelkasten corpus for version 1.
- Discovery should use a simple weighted relevance pass first to gather candidate notes.
- Candidate sources may include PKM notes whose titles, tags, contacts, links, or terms overlap with the source analysis.
- The first pass is expected to over-retrieve rather than be precise.
- Retrieved material should be added to the temporary working context for later filtering.
- Weighted relevance should prioritize tag matches and title matches first.
- Link tracing should carry the next strongest weight.
- General term matching across the PKM should be used as a broader, lower-precision retrieval layer.

* Reference material filtering
- A second pass should remove irrelevant or low-value context filler from retrieved candidates.
- Filtering should optimize for relevance to actions, follow-up, prior decisions, constraints, and context needed to interpret the source item correctly.
- The filter should preserve unusual implementation details, contact-specific preferences, and project-specific constraints when they materially affect what should happen next.

* Review and retry controls
- The human should be able to edit the source slice sent to the model before a retry.
- The human should be able to add or change prompt instructions before a retry.
- The human should be able to choose whether to continue locally or switch to a cloud stage after review.
- Any edited source, context, or prompt should require approval before being sent to an LLM.
- Actions should be represented more as selection from valid paths than unconstrained free text generation.
- Source text, context packages, and prompts should remain editable free text in the control workflow.
- The control buffer should behave like a guided workflow, showing stages already run and only currently valid next actions.
- The interface should preserve visibility into what has happened and what context is being used.

* Cloud sanitization rules
- Replace names with roles
- Remove email addresses
- Remove URLs
- Anonymize client companies and contacts
- Rewrite identifying business context into generalized descriptions
- Keep non-identifying technical terms
- Remove internal project names
- Any cloud pass must happen only after human review and explicit approval
- After a cloud action, the local LLM should reintegrate returned output into the original non-anonymized local context
- Any reasoning stage may switch to cloud processing if the sanitization path is followed first

* Cloud-pass mechanics
- Any reasoning stage may be routed through cloud processing as long as it can pass through the sanitization path first.
- A cloud pass should follow this sequence: prepare sanitized package, allow manual edits to the package, show the package for review, approve send, run the cloud stage, show the returned result, and approve candidate reintegration.
- The sanitized package should contain the same kinds of material that would have been included in the non-sanitized stage input, with names and client-sensitive data obscured according to the active sanitization rules.
- The sanitized package should remain editable before send, just like local stage context and prompt material.
- Cloud output should be shown first as a candidate merge back into the main local working context rather than being reintegrated automatically.
- If a cloud pass fails, times out, or returns poor output, the workflow should not assume a fallback path automatically.
- After a cloud pass problem, the human should decide whether to retry, edit and retry, fall back to local processing, skip, or abort.
- The audit log should record both the sanitized package that was actually sent and the reintegrated local result that was ultimately accepted.
- Redaction policy may be controlled through prompt design, and cloud use for a given stage may also be disabled through configuration variables.

* Stage transition rules
- After `Inspect source`, valid next actions should include `Match project`, `Discover relevant reference material`, `Decide on cloud pass`, `Retry inspect`, and `Abort`.
- After `Match project`, a matched or ambiguous result should still allow the human to disagree and choose a manual match or propose a new project.
- After `Match project`, a matched project should unlock `Discover relevant reference material`, `Extract actions`, `Extract waiting-for`, and `Suggest reference notes`.
- After `Match project`, an ambiguous result should allow manual project choice, retry, disagreement with the match result, and new-project creation.
- After `Match project`, a no-match result should allow manual match, retry, and new-project creation.
- `Discover relevant reference material` should require `Inspect source` to have run first.
- `Filter useful reference material` should require `Discover relevant reference material` to have run first.
- `Extract actions`, `Extract waiting-for`, and `Suggest reference notes` should be runnable independently and in any order once sufficient context exists.
- `Suggest reference notes` may be used to suggest a general PKM note before project context exists if the human chooses that path.
- `File approved outputs` should become available only when there is at least one approved artifact or change candidate ready to file.
- `Integrate into source` should be available after any major stage output, not only after cloud-returned results.

* Prompt execution contract
- Every stage execution should follow the same base contract: resolve prompt ID, assemble the context package, optionally sanitize, allow human edits, submit to the selected model, capture raw output, normalize into a stage result, and present the result for review.
- Stage outputs should be normalized into Org-native forms so they are easier to inspect, edit, and reuse inside Org workflows.
- If a model returns malformed output, `delib-flow` should attempt one automatic local repair pass before surfacing raw output for human review.
- If repair does not succeed, the raw output should be shown and the human should decide how to proceed.
- Prompt execution should always record prompt ID, prompt version, selected model or provider, exact input package, and raw output.
- When the human manually edits a context package before execution, that edited package should become the canonical input snapshot for that attempt.
- The package architecture should make stage-specific postprocessors feasible even if version 1 keeps normalization simple.
- The package architecture should also make future additional stages feasible without redesigning the execution contract.

* Deterministic insertion contract
- Version 1 should support first-class filing actions for creating a project item, inserting a next-action child, inserting a waiting-for child, updating a project metadata drawer, creating a project support note, creating a general PKM note, and inserting or updating a project link to a support note.
- Version 1 metadata updates should remain limited to tags, contacts, reference file links, and optional checklist fields.
- Each filing action should target exactly one artifact or location at a time.
- Coupled changes should remain separate filing actions rather than a single composite action.
- Filing actions should rely on normal Emacs buffer or capture operations so standard undo behavior is sufficient.
- Filing previews should show only final rendered Org blocks, without a low-level diff or patch view.
- If a filing target has changed since preview preparation, `delib-flow` should warn the human and let the human decide how to proceed.
- General PKM note creation should always go through the configured capture template.
- Project support note creation should also follow the configured capture-template path when capture is used for that artifact.

* Validation policy matrix
- Validation behavior should be configurable per rule through variables, with defaults enabled in warning mode.
- Project item creation validations for title safety or length, state presence, presence of a next action or waiting-for item, required tags, and contacts should all default to warnings.
- Project item warnings should allow the human to manually resolve the issue, retry, or ignore the warning.
- Next-action validations for pomodoro-sized scope, direct executability, and clear context should default to warnings.
- Weak next-action outputs should warrant one automatic retry before being surfaced for human review.
- Waiting-for validations for explicit blocker or dependency, linked or plain-text contact when applicable, and current blocked-state phrasing should default to warnings.
- For reference-note creation, required Org-roam fields should be treated as blocking validations.
- Other note validations such as title presence, tags, and broader reuse justification for PKM notes should default to warnings.
- When a blocking validation prevents filing, the control workflow should allow the human to edit and retry.

* Audit-log entry format
- The audit log should use one top-level Org heading per workflow run.
- Run headings should be timestamp-first in their title.
- Each executed stage should appear as a nested heading under the run heading.
- The run heading should include compact machine-usable properties such as source link, started-at timestamp, and run status.
- Run status should support at least `completed`, `aborted`, and `partial`.
- Stage headings should include compact machine-usable properties such as stage name, prompt ID, prompt version, model provider, model name, started-at timestamp, ended-at timestamp, approval state, and input snapshot reference.
- Stage subtrees should contain foldable content sections for the exact input package, raw output, normalized result, and human edits when present.
- A separate approval-note subtree is not required for version 1; the approval property is sufficient.

* Control-buffer content contract
- The control buffer should use a stable top-level heading layout in this order: `Source`, `Working context`, `Stage history`, `Current decision`, `Valid next actions`, `Filing preview`, and `Audit status`.
- The `Source` section should contain the frozen source snapshot captured when the workflow started, along with source type.
- The `Working context` section should contain the current merged context model, including the latest inspect output, retained snippets, and accepted manual edits.
- The `Working context` section should also contain a visible subsection for the sanitized cloud package whenever one is being prepared or reviewed.
- The `Stage history` section should contain one subtree per executed stage.
- Stage-history subtrees should default to collapsed except for the latest stage.
- Each stage subtree should show the normalized result prominently, with prompt text, input package, raw output, and related artifacts under foldable subheadings.
- The `Current decision` section should represent the current unresolved operator choice.
- The `Valid next actions` section should contain only actions that are currently legal from the present run state.
- The `Filing preview` section should show rendered Org blocks for approved filing actions when such actions exist.
- The `Audit status` section should show current run status, audit-path readiness, and whether stage data is ready to append.

* Error and interruption semantics
- If the human explicitly aborts a run, the control buffer should close immediately.
- If a local or cloud model call times out, the timeout should be surfaced in the `Current decision` section.
- After a timeout, the workflow should offer retry, edit and retry, switch between local and cloud where valid, skip, or abort.
- If a stage output is malformed and the one automatic repair pass also fails, the raw output should be shown in stage history.
- If malformed output cannot be repaired, no normalized result needs to be forced; the workflow should present the raw output and let the human decide what to do next.
- If a filing action partially changes a target before failing, `delib-flow` should surface the resulting buffer state and warn the human.
- In version 1, `delib-flow` should not attempt rollback for partial filing failures.
- Because saving remains a manual human action, the human remains responsible for resolving partially changed buffers.
- Partial filing failures should still be surfaced clearly for diagnostics.
- If a required external dependency goes missing mid-run, the workflow should keep the run alive and block only the dependent actions.
- Blocked actions should show the reason they are currently unavailable.
- The workflow does not need to warn before the control buffer is closed.
- A run should still count as a success when filing actions were handled appropriately or when the workflow determined that no filing actions were needed.

* External dependency contract
- Org-roam should be treated as optional but strongly preferred for version 1.
- Org-roam should create stage-level dependencies rather than a hard package dependency.
- `delib-flow` may assume that the Org-roam database is already available and up to date.
- Search should prefer `rg`, and version 1 may treat `rg` as a required dependency if that materially hardens retrieval behavior.
- Capture templates for project support notes and general PKM notes should have package-provided defaults when no user configuration is supplied.
- Local model access should use one configurable adapter interface in version 1 rather than multiple built-in provider backends.
- Cloud model access should also use one configurable adapter shape in version 1.
- Missing cloud adapter configuration should block only cloud-dependent features.
- `delib-flow` should remain fully usable as a local-only workflow when no cloud support is configured.

* Minimal version-1 scope cut
- Version 1 inputs should be limited to imported email Org items and meeting notes in daily notes.
- Version 1 model paths should include a fully local workflow and an optional cloud path that operates only through sanitization.
- Version 1 stage coverage should include `Inspect source`, `Match project`, `Discover relevant reference material`, `Filter useful reference material`, `Propose new project`, `Extract actions`, `Extract waiting-for`, `Suggest reference notes`, `Decide on cloud pass`, `Sanitize for cloud`, `Integrate into source`, and `File approved outputs`.
- Version 1 filing actions should include creating a project item, inserting a next-action child, inserting a waiting-for child, updating a project metadata drawer, creating a project support note, creating a general PKM note, and inserting or updating a project support-note link.
- Explicitly deferred beyond version 1 should be automated inbox ingestion from Outlook, multiple simultaneous runs, richer UI customization, richer metadata editing, anti-example support, multiple provider-specific built-in backends, and post-project review or archive automation.

* Steps
- Human places point on an email org item or meeting note in Emacs.
- Workflow analyzes the source item without modifying it.
- Inspect source should extract summary, entities, contacts, terms, commitments, dates, blockers, decisions, questions, links, and notable statements.
- Source inspection may run multiple times, with each pass enriching the working context for the next action.
- Workflow checks for an associated project in the My Projects roam file.
- Project matching should use project names, tags, links, contacts, and related metadata.
- The workflow should present one best-guess project match with reasons.
- The human can reject the match, ask for another attempt, or provide the correct project directly.
- Human guidance can refine tags or metadata to improve future matching.
- The workflow can discover relevant reference material by generating search terms and running a weighted candidate retrieval pass across the PKM.
- Directly attached project reference material should also be checked when available.
- Retrieved candidates should be filtered in a second pass to remove low-value context filler before being used downstream.
- If no project is found, workflow collaborates with the human to define a new project through a project start checklist.
- Mandatory and optional checklist items should be distinguished, and optional items should be selectable by the human.
- Workflow proposes atomic actions, one next action, possible follow-up actions, waiting-for items, and candidate reference notes.
- Atomic actions should be directly executable in a specific context and fit within one 25-minute pomodoro.
- Each step is reviewable, regeneratable, and manually adjustable before moving to the next step.
- At each stage, the human can choose to continue locally or prepare a sanitized cloud pass.
- Any reasoning stage may be routed through cloud processing after sanitization and explicit approval.
- Waiting-for includes delegated tasks and any dependency that blocks further project progress.
- The workflow may determine that an item is non-actionable and should be archived or kept only as reference.
- For non-actionable items, the system may propose a general PKM reference note, project support material, or archive handling, with the final choice left to the human.
- Existing project next actions should be filed as direct TODO children under the project item and tagged `next_action`.
- Existing project waiting-for items should be filed as direct WAITING children under the project item.
- Projects should stay under Active if there is any action available to move them forward.
- Projects should move under Waiting only when no further action can currently move them forward.
* Artifact Enrichment Redesign

The current filing-centric model still conflates four different operator concerns:

- finding candidate artifacts
- selecting which artifact is worth pursuing
- enriching one artifact into a stronger draft
- filing or executing the finished artifact

That interaction model is weakest for note drafting, but the same structural issue exists for actions, waiting-fors, and project proposals. The operator should not need to treat broad candidate generation as if it already produced a finalized artifact.

** Target Interaction Model

The intended operator loop for all enrichable artifact types is:

1. find candidate artifacts
2. select one candidate
3. enrich the selected candidate
4. review or regenerate only that selected candidate
5. file or execute the selected enriched candidate

This should replace the current model where one stage often tries to generate several artifacts at once and filing becomes the first place where a concrete draft feels real.

** Applicable Artifact Families

This redesign applies to all enrichable artifact families:

- actions
- waiting-fors
- reference notes
- project proposals

Each family can still have family-specific rules and prompts, but they should share the same control-flow model.

** Shared State Model

Each artifact family should expose two distinct layers of state:

1. Candidate state
   - lightweight shortlist
   - item text or title
   - item kind or subtype
   - explanation or why-this-might-matter
   - warnings
   - suggested tags

2. Selected draft state
   - selected candidate identifier
   - enriched or drafted body
   - targeted supporting material
   - regeneration history
   - filing preview

The current filing state should stop carrying the whole burden of candidate discovery, selected draft state, and filing consequence at the same time.

** Stage Design

Each enrichable artifact family should be split into two conceptual stage layers:

1. Finder stages
   - broad candidate discovery
   - shortlist-oriented
   - cheap enough to rerun
   - not responsible for full drafting

2. Enrichment stages
   - operate on the selected candidate only
   - generate the concrete content that will later be filed or executed
   - can be rerun without disturbing unrelated candidates

Suggested naming direction:

- Find Actions
- Draft Selected Action
- Find Waiting-Fors
- Draft Selected Waiting-For
- Find Reference Notes
- Draft Selected Note
- Find Project Candidates
- Draft Selected Project

The current stage names can be preserved initially for compatibility, but the design intent should follow this split.

** Regeneration Semantics

Regeneration should be item-local, not batch-global.

When the operator wants another pass:

- preserve the candidate shortlist
- preserve the current selection
- replace only the selected item draft
- preserve other unrelated artifacts

For example, if the operator selects one note candidate and asks for regeneration, only that note draft should change. The rest of the note shortlist should remain stable.

** Retrieval and Supporting Material

Discovery and filtering should be able to operate both:

- broadly, before selection
- narrowly, after selection

The selected-item path is especially important. Once the operator chooses one artifact, supporting material should be targeted to that artifact's focus rather than to the entire source.

This is expected to improve quality for:

- reference note drafting
- project proposal rationale
- action clarification
- waiting-for ownership and framing

** Filing Role

Filing should become the final staging step for an already enriched selected artifact.

It should no longer act like the place where:

- note bodies first materialize
- project proposals first become concrete
- action wording is first made specific

The operator should arrive at filing with one selected enriched artifact that already has:

- readable preview
- consequence preview
- target preview

** Control Buffer Implications

For each artifact family, the control buffer should converge on the same loop:

- Candidate shortlist
- Selected item
- Draft preview
- Regenerate selected item
- Planned target or consequence
- File or execute selected item

This is the simplest model for operator comprehension on both desktop and narrow terminal/mobile use.

** Why This Model Is Better

- prompts become smaller and more specific
- regeneration becomes predictable
- retrieval can specialize to one artifact
- filing becomes easier to understand
- the operator sees a stable shortlist plus one active draft
- authored artifacts feel authored rather than batch-generated

** Pilot Recommendation

Reference notes should be the first pilot for this redesign because:

- the current pain is clearest there
- drafting quality benefits most from narrower prompts
- the existing filing loop already exposes much of the needed preview surface

After notes, the same model should expand to actions, waiting-fors, and project proposals.
